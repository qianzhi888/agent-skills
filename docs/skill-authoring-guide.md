# Skill 编写指南

> 从 7 个生产级技能的实践中提炼的编写方法论。一个好的 Skill = **明确的触发条件 + 可执行的步骤 + 完备的异常处理 + 清晰的安全边界**。

## 一、结构规范

```markdown
---
name: skill-name            # 唯一标识，小写+连字符
description: 一句话说明做什么。列出触发词："xx"、"yy"即可触发。
license: MIT
metadata:
  author: xxx
  version: "1.0"
---

# 技能标题
> 一句话定位（这个技能的核心价值）

## 触发场景 / 输入
## 执行流程（编号步骤）
## 输出格式
## 禁止事项
```

## 二、六条核心原则

### 1. description 是技能的"入口路由"

Agent 靠 description 决定是否加载技能，必须包含：
- **做什么**：一句话讲清功能
- **触发词**：用户可能说的自然语言（"提交代码"、"切图"、"review"）

❌ `description: 代码提交工具`
✅ `description: 自动提交代码并推送。说"提交代码"、"推送"、"commit"即可触发。`

### 2. 步骤必须可执行，不能只是"指导"

每一步给出具体命令、判断条件、产出物，让 Agent 无需临场发挥：

❌ "分析代码变更，生成合适的 commit message"
✅ "执行 `git diff --name-only HEAD`，按文件路径识别模块，总结控制在 20 字以内"

### 3. 每个步骤都写异常分支

生产环境的技能，异常路径比正常路径更重要。格式：

```markdown
**异常处理**：
- ❌ 分支名中无数字 → 提示用户手动输入编号
- ❌ push 失败（无远程分支） → 使用 `git push --set-upstream origin {branch}`
```

### 4. 用 ✅/❌ 对比压缩歧义空间

LLM 对"好/坏示例对比"的遵循度远高于抽象描述：

```markdown
**好的示例**：`新机商城列表、详情、搜索` — 具体指出了三个功能页面
**差的示例**：❌ `页面修改` — 太笼统
```

### 5. 危险操作设置确认检查点

提交代码、覆盖文件、删除资源前，强制要求用户确认：

```markdown
❌ **禁止在用户未确认前直接提交**：必须展示 commit message 让用户确认
```

### 6. 以"禁止事项"收尾，划定红线

把绝对不能做的事集中列出（force push、跳过 hooks、硬编码密钥等），这是技能的安全底线。

## 三、进阶技巧

| 技巧 | 说明 | 案例 |
|------|------|------|
| **真实案例库** | 在技能末尾附真实使用案例，Agent 照葫芦画瓢准确率大幅提升 | zmn-flutter-api-integration 的 4 个联调案例 |
| **前置依赖检查** | 依赖外部工具时，首次执行先检查环境，缺失时给出安装命令 | zmn-flutter-figma-cutout-png 的 rsvg-convert/pngquant 检查 |
| **决策树分流** | 多分支场景用表格/决策树明确路由条件 | "有返回数据/无返回数据"两种联调模式 |
| **闭环沉淀** | 让技能产出的经验反哺规则库，形成飞轮 | zmn-flutter-session-review 提炼规则回写 |
| **标准化输出** | 定义固定输出模板，结果可预期、可对比 | 切图完成报告、调试报告格式 |
| **Token 意识** | 高频内容精简（速查表），低频细节按需加载 | session-review 的 always_on/model_decision 分层 |

## 四、质量自检清单

编写完成后逐项检查：

```
□ description 包含触发词，陌生人看一眼知道何时会用到
□ 每个步骤都有明确的输入、动作、产出
□ 每个可能失败的步骤都有异常处理
□ 危险操作有确认检查点
□ 至少一组 ✅/❌ 对比示例
□ 有"禁止事项"章节
□ 输出格式有固定模板
□ 换一个人（或下一次会话的 Agent）能无歧义执行
```
