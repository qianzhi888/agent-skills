# 周报自动生成

> 基于 git 提交历史等客观数据自动汇总，**杜绝周报编造与流水账**：按需求聚合、突出产出与进展、暴露风险。

## 触发场景

- 用户说"写周报"、"生成周报"、"总结这周做了什么"
- 周五/周一定期汇报
- 用户提供时间范围（"上周的"、"最近两周"）

## 输入

| 信息 | 必填 | 说明 |
|------|------|------|
| 时间范围 | 可选 | 默认本周一 00:00 至今；可指定"上周"、具体日期区间 |
| 仓库范围 | 可选 | 默认当前仓库；用户可提供多个仓库路径汇总 |
| 补充事项 | 可选 | git 之外的产出（评审、联调沟通、文档），由用户补充 |

---

## 执行流程

### 步骤 1：确定时间范围

```bash
# 本周一至今（macOS date）
SINCE=$(date -v-Mon +%Y-%m-%d)

# 上周：date -v-7d -v-Mon
# 用户指定区间：直接使用
```

### 步骤 2：采集提交记录

```bash
# 当前用户在时间范围内的提交（自动识别作者）
git log --author="$(git config user.name)" \
  --since="$SINCE" --pretty=format:"%h|%ad|%s" --date=short

# 涉及的文件范围（用于判断模块）
git log --author="$(git config user.name)" --since="$SINCE" --name-only --pretty=format:"%h %s"
```

多仓库场景：对每个仓库路径重复上述命令。

**异常处理**：
- ❌ 时间范围内无提交 → 询问用户是否扩大范围，或由用户口述本周工作
- ❌ 提交在其他分支未合并 → 补充 `--all` 参数重新采集

### 步骤 3：按需求聚合（核心步骤）

**禁止逐条罗列 commit**，必须按业务需求聚合：

1. 从 commit message 提取需求标识（编号、需求名）
2. 同一需求的多次提交合并为一条产出
3. 区分状态：
   - 已合入主干 → **已完成**
   - 仍在功能分支 → **进行中**（注明进度，如"联调中"、"待提测"）
   - 本周新增的探索性分支 → **新启动**

聚合示例：

```
❌ 流水账：修复列表bug；优化样式；改接口；再改接口
✅ 聚合：【换新优化】新机商城列表、详情、搜索对接完成，修复价格显示问题（已提测）
```

### 步骤 4：补充 git 之外的产出

询问用户（如未主动提供）：

> "本周是否有 git 之外的工作？例如：需求评审、技术方案讨论、线上问题支持、帮同事排查问题"

### 步骤 5：生成周报

---

## 输出格式

```markdown
## 周报（MM.DD - MM.DD）

### ✅ 本周完成
1. 【需求名】产出描述（结果/数据，如已上线、已提测）
2. ...

### 🚧 进行中
1. 【需求名】当前进度 —— 预计完成时间

### ⚠️ 风险与求助
- （阻塞项、依赖方未就绪、需要协调的资源；没有则写"无"）

### 📅 下周计划
1. ...

### 📌 其他
- 评审/支持/文档等非代码产出
```

**撰写原则**：
- ✅ 结果导向：写"完成了什么、达到什么状态"，不写"做了什么动作"
- ✅ 有量化尽量量化：页面数、接口数、修复问题数
- ✅ 风险前置：阻塞项必须显式写出，周报是暴露风险的渠道
- ❌ 不夸大、不编造：只汇总有证据（commit/用户确认）的内容

**异常处理**：
- ❌ 用户要求写入无依据的"产出" → 照做但提醒该内容无 git 记录支撑

### 步骤 6：确认与输出

展示周报草稿 → 用户修改确认 → 输出最终版（Markdown，可直接粘贴到 IM/邮件/文档）。

## 禁止事项

- ❌ **禁止罗列原始 commit**：必须按需求聚合提炼
- ❌ **禁止编造产出**：每条完成项必须有 commit 或用户确认作为依据
- ❌ **禁止隐藏风险**：本周遇到的阻塞必须体现在"风险与求助"栏
- ❌ **禁止未经确认直接发送**：周报涉及对外汇报，必须用户确认终稿
