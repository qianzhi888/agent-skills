# 结构化代码审查

> 不做泛泛而谈的"建议加注释"式审查，只输出**高信号问题**：逻辑缺陷、安全隐患、性能陷阱、边界遗漏。

## 触发场景

- 用户说"review"、"审查代码"、"帮我看看这段代码有没有问题"
- 完成一个功能开发、准备提交前
- 用户提供一段代码/一个 diff 请求评估质量

## 审查范围确定

| 输入 | 范围 |
|------|------|
| 用户指定文件/代码段 | 仅审查指定内容 |
| 说"review 本次改动" | `git diff HEAD` + 未追踪文件 |
| 说"review 这个 PR" | 目标分支与当前分支的完整 diff |

**审查前先建立上下文**：读取变更文件的完整内容（不只看 diff），理解改动在整个模块中的位置与调用关系。

---

## 审查维度（按严重程度加权）

### 维度 1：逻辑正确性（最高优先级）

- ❓ 边界条件：空值、空数组、0、负数、最大值、单元素
- ❓ 分支完整性：switch/if 是否覆盖所有情况，是否有遗漏的 else
- ❓ 并发与时序：异步竞态、重复提交、请求返回时页面已销毁
- ❓ 状态一致性：多处更新同一状态时是否可能不同步
- ❓ 错误处理：异常是否被吞掉、失败路径是否有兜底

### 维度 2：安全性

- ❓ 注入风险：SQL 拼接、命令拼接、XSS（未转义的用户输入渲染）
- ❓ 敏感信息：硬编码密钥/Token、日志打印密码、明文存储
- ❓ 权限校验：接口/操作是否校验了当前用户权限
- ❓ 信任边界：是否直接信任了客户端传来的 ID、金额、状态

### 维度 3：性能

- ❓ 循环中的重复计算/重复 IO（N+1 查询）
- ❓ 大数据量场景：列表是否有分页/虚拟化、是否全量加载
- ❓ 不必要的重渲染/重复请求
- ❓ 资源泄漏：未关闭的连接、未清理的定时器/监听器

### 维度 4：可维护性（只报影响理解的问题）

- ❓ 命名与实现不符（误导后续维护者）
- ❓ 魔法数字散落多处、同一常量重复定义
- ❓ 死代码、注释掉的代码块
- ❓ 重复代码超过 10 行且明显可抽取

> **不报**：纯风格偏好（缩进、引号）、"建议加注释"式空话、与本次变更无关的历史问题。

## 执行流程

### 步骤 1：收集变更

```bash
git diff HEAD --stat          # 变更概览
git diff HEAD                 # 完整 diff
git ls-files --others --exclude-standard  # 新文件
```

### 步骤 2：逐文件深度阅读

对每个变更文件：
1. 读取**完整文件**（不只是 diff 片段），理解上下文
2. 定位变更的调用方与被调用方，检查契约是否仍然成立
3. 按四个维度逐项核对

### 步骤 3：验证疑点

对每个疑似问题，先验证再报告：
- 怀疑某变量可能为空 → 追溯其赋值来源确认
- 怀疑接口未校验 → 实际读取校验代码确认
- **不确定的问题标注 ⚠️ 待确认，不当作结论**

### 步骤 4：输出报告

---

## 输出格式

```markdown
## 🔍 Code Review 报告

**审查范围**：N 个文件，+X/-Y 行
**总体评价**：✅ 可合入 / ⚠️ 修复后合入 / ❌ 需要重构

### 🔴 必须修复（阻塞合入）
1. **[逻辑] 文件:行号** — 问题描述
   - 触发场景：xxx
   - 建议修复：（给出具体代码）

### 🟡 建议修复（不阻塞但应处理）
...

### 🔵 可选优化
...

### ✅ 亮点
（值得肯定的设计，1-2 条即可，没有则省略）
```

**问题描述规范**：
- ✅ 必须给出**触发场景**（什么情况下会出问题），不接受"这里可能有问题"
- ✅ 修复建议必须**具体到代码**，不接受"建议优化此处"
- ✅ 标注维度标签：`[逻辑]` `[安全]` `[性能]` `[可维护]`

## 禁止事项

- ❌ **禁止罗列风格问题凑数**：没有高信号问题就说"未发现问题"
- ❌ **禁止只看 diff 不看上下文**：脱离上下文的审查必然误判
- ❌ **禁止未验证就下结论**：疑点必须追溯代码确认
- ❌ **禁止修改代码**：本技能只审查、只建议，改动由用户决定
