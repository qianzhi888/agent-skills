# 自动提交代码并推送

> 自动生成规范格式的 commit message，完成 `git add → commit → push` 全流程。

## Commit Message 格式

```
[分支编号] [all] 需求名称 改动点摘要
```

**示例**：`[5104497] [all] 换新优化 新机商城列表、详情、搜索`

| 部分 | 来源 | 说明 |
|------|------|------|
| `[分支编号]` | 自动提取 | 从当前分支名中提取数字（如 `feature/jinqianzhi_5099640_newMachine` → `5099640`） |
| `[all]` | 固定 | 固定格式 |
| 需求名称 | 用户输入 | 向用户询问本次需求名称 |
| 改动点摘要 | 自动生成 | 分析 `git diff` 自动总结，尽量简短 |

## 输入

执行技能时，可选提供：

| 信息 | 必填 | 说明 |
|------|------|------|
| 需求名称 | ✅ | 如未提供，会主动询问 |
| 改动点摘要 | 可选 | 如未提供，自动分析 git 变更生成 |

**如用户未提供需求名称**，询问：
> "请提供本次提交的需求名称（例如：换新优化、工单详情改版）"

**如用户同时提供了需求名称和改动点**，直接使用用户提供的内容，跳过自动分析。

## 执行流程

### 步骤 1：检查工作区状态

```bash
git status --short
```

- 如果没有任何变更 → 提示用户 "当前没有需要提交的变更" 并终止
- 如果有变更 → 继续

### 步骤 2：提取分支编号

```bash
git branch --show-current
```

从分支名中提取数字部分：
- `feature/jinqianzhi_5099640_newMachine` → `5099640`
- `feature/zhangsan_1234567_orderDetail` → `1234567`
- 提取规则：分支名按 `_` 分割，取**纯数字**的那一段（通常是第二段）

**异常处理**：
- ❌ 分支名中无数字 → 提示用户手动输入编号
- ❌ 不在任何分支上（detached HEAD） → 提示用户切换到开发分支

### 步骤 3：分析变更内容

```bash
# 查看所有变更文件
git diff --name-only HEAD

# 查看已暂存的变更
git diff --cached --name-only

# 查看未暂存的变更
git diff --name-only

# 查看未追踪的新文件
git ls-files --others --exclude-standard
```

**分析维度**（按优先级）：

1. **读取变更内容**：不仅看文件路径，还要通过 `git diff` 读取具体代码变更，理解改了什么功能
2. **识别模块**：根据文件路径判断属于哪个业务模块（如 `modules/renewal/` → 换新模块）
3. **识别功能点**：根据代码变更内容，明确指出具体的功能改动（如 "新增搜索功能"、"修复价格显示"、"优化列表加载"）
4. **区分新增/修改/修复**：
   - 新增文件 → "新增XX页面"、"新增XX功能"
   - 修改文件 → "优化XX"、"调整XX"
   - 修复bug → "修复XX问题"

**总结原则**：
- ✅ **具体明确**：说清楚改了什么功能，不能太笼统（如 "新机商城列表、详情、搜索" 而非 "商城相关"）
- ✅ 用顿号分隔：多个改动点用 `、` 连接
- ✅ 描述功能而非文件：说 "列表页、详情页" 而非 "view.dart、logic.dart"
- ✅ **适当精炼**：控制在 20 字以内，但不能丢失关键信息
- ❌ 不要罗列文件名
- ❌ 不要过于笼统（如 "页面修改"、"代码优化"）

**好的示例**：
- `新机商城列表、详情、搜索` — 具体指出了三个功能页面
- `订单取消页面、取消原因选择` — 明确了具体改动点
- `修复价格显示精度、优化加载动画` — 区分了修复和优化
- `新增订单信息入口、对接详情接口` — 区分了新增和对接

**差的示例**：
- ❌ `页面修改` — 太笼统
- ❌ `代码优化` — 没有具体内容
- ❌ `更新了一些文件` — 毫无信息量

### 步骤 4：询问需求名称（如未提供）

如果用户在触发技能时没有提供需求名称，使用 `ask_user_question` 工具询问：

> "请提供本次提交的需求名称（例如：换新优化、工单详情改版）"

### 步骤 5：确认 commit message

将组装好的 commit message 展示给用户确认：

```
即将提交：[5099640] [all] 换新优化 新机商城列表、详情、搜索

变更文件数：12 个文件
```

使用 `ask_user_question` 让用户确认或修改：
- 确认提交
- 修改 commit message

### 步骤 6：执行提交和推送

```bash
# 添加所有变更
git add -A

# 提交
git commit -m "[分支编号] [all] 需求名称 改动点摘要"

# 先拉取远程最新代码（合并方式）
git pull origin HEAD

# 推送到远程（当前分支）
git push origin HEAD
```

**异常处理**：
- ❌ commit 失败（如 hook 拦截） → 展示错误信息，询问用户如何处理
- ❌ pull 失败（如有冲突） → 展示冲突文件列表，提示用户手动解冲突后执行 `git add` + `git merge --continue`，再重新 push
- ❌ push 失败（无远程分支） → 使用 `git push --set-upstream origin {branch}` 推送

### 步骤 7：输出结果

```
✅ 代码提交并推送成功
- 分支：feature/jinqianzhi_5099640_newMachine
- Commit：[5099640] [all] 换新优化 新机商城列表、详情、搜索
- 变更文件数：12 个文件
- 远程：已推送到 origin
```

## 禁止事项

- ❌ **禁止在用户未确认前直接提交**：必须展示 commit message 让用户确认
- ❌ **禁止 force push**：不使用 `--force` 或 `--force-with-lease`
- ❌ **禁止修改 git config**：不修改用户的 git 配置
- ❌ **禁止跳过 git hooks**：不使用 `--no-verify`
